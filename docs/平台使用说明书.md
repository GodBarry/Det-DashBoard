# Det Dashboard 平台使用说明书

版本：当前仓库版本  
适用对象：数据管理员、标注人员、模型/算法使用人员、训练与评估人员

## 1. 平台定位

Det Dashboard 是面向目标检测数据集的模型全生命周期工作台。平台把数据集、标注、算法适配器、Python 环境、模型权重、训练任务、推理任务和评估结果串联起来，形成：

```text
数据导入 → 数据治理/标注 → 资产登记 → 训练 → 推理 → 评估 → 结果复盘
```

平台的核心数据分工如下：

| 内容 | 主要存储 | 用途 |
| --- | --- | --- |
| 项目、文件夹、图片记录、标注、任务状态、权限 | PostgreSQL | 查询、筛选、关联、统计和权限控制 |
| 图片、视频、LabelMe JSON、导出文件、模型文件、算法源码、Python 环境包 | MinIO | 非结构化对象的持久化存储 |
| 缩略图、临时缓存、运行日志、任务工作目录 | 运行缓存目录 | 加速访问和执行任务，不作为唯一归档来源 |
| 原始数据源 | 宿主机可浏览目录 | 导入来源；独立对象模式下导入后可脱离原路径使用 |

MinIO 的目录内部可能出现 `xl.meta` 等对象存储内部文件。它们是 MinIO 的实现细节，不是用户应直接复制、改名或删除的业务文件。模型、算法和 Python 环境应通过平台资产入口导入、登记、下载或导出。

## 2. 启动与停止

### 2.1 Windows + Podman 一键启动

在 PowerShell 中进入项目目录：

```powershell
cd E:\projects\Det-DashBoard
.\restart-det-dashboard-podman.bat
```

脚本会依次：

1. 停止 4177、5173、PostgreSQL 和 MinIO 的旧进程/隧道。
2. 启动 Podman machine 和 Podman socket。
3. 重新挂载 Windows 运行目录并启动 PostgreSQL。
4. 启动 MinIO。
5. 建立 Windows 到 Podman machine 的 SSH 隧道。
6. 启动 Node.js API。
7. 启动 Vite 前端并检查健康状态。

默认地址：

| 服务 | 地址 |
| --- | --- |
| Web 前端 | http://127.0.0.1:5173/ |
| Node API | http://127.0.0.1:4177/ |
| PostgreSQL | `127.0.0.1:15432` |
| MinIO API | `http://127.0.0.1:9000` |
| MinIO Console | `http://127.0.0.1:9001` |

默认运行目录：

```text
E:\projects\DD-runtime\postgres   PostgreSQL 数据
E:\projects\DD-runtime\minio       MinIO 数据
E:\projects\DD-runtime\cache       缩略图和任务缓存
E:\projects\DD-runtime\logs        API、Web、Podman 隧道日志
E:\projects\DD-runtime\data-root   默认浏览根目录
```

如果 Node.js 不在运行目录中，脚本会回退到 `D:\Program Files\nodejs\npm.cmd`。如果 Podman machine 不可连接，先执行：

```powershell
podman machine list
podman machine start
podman system connection list
```

然后再次运行启动脚本。不要同时手动启动另一套 PostgreSQL、MinIO 或 Node 服务，否则端口和数据库连接可能冲突。

### 2.2 Ubuntu 24.04 迁移部署

项目提供 `migration/ubuntu24.04` 迁移包。将镜像 tar、配置和脚本复制到 Ubuntu 后：

```bash
cd ubuntu24.04
chmod +x load-images.sh start.sh stop.sh verify.sh
./load-images.sh
cp .env.example .env
# 编辑 .env，设置强密码、端口和数据目录
./start.sh
./verify.sh
```

迁移前应保存 PostgreSQL 数据目录、MinIO 数据目录、`.env` 和导出目录。生产环境应在反向代理后使用 HTTPS，并限制 PostgreSQL/MinIO 管理端口的访问范围。

### 2.3 停止和日志

Windows 关闭服务可再次运行启动脚本，脚本会先清理旧服务。诊断时优先查看：

```text
E:\projects\DD-runtime\logs\api.log
E:\projects\DD-runtime\logs\web.log
E:\projects\DD-runtime\logs\podman-tunnel.log
```

健康检查：

```powershell
Invoke-WebRequest http://127.0.0.1:4177/api/health/live
Invoke-WebRequest http://127.0.0.1:4177/api/health/ready
```

## 3. 登录、账号与权限

打开前端后先登录。首次初始化会创建默认管理员：

```text
用户名：admin
密码：admin
```

首次登录后应立即修改密码，并避免在生产环境继续使用默认密码。普通用户可在登录窗口注册，默认角色为普通用户。

### 3.1 管理员与普通用户

- 管理员：管理用户、权限、公共资源、发布申请、标注规范、术语映射和审计记录。
- 普通用户：查看和使用有权限的数据集/资产，创建自己的任务，按权限申请共享或公开。
- 公共资源：通过管理员审核后，对有访问权限的用户可见；底层对象只保存一份，不为每个用户复制一份。
- 私有资源：默认归创建者所有；通过分享邀请、权限设置或公开申请授予其他用户访问权。

账号菜单可以查看当前用户、退出登录。管理员中心可处理用户状态、资源权限、共享邀请和公开申请。

### 3.2 数据集协同标注

管理员或有权限的用户可创建协同标注任务，并将图片项分配给标注人员。标注人员领取任务后获得锁，完成后提交；管理员负责审核、退回或通过。锁需要续租，异常退出后可由系统释放或由管理员处理。

## 4. 数据集工作区

顶部“数据集”进入数据集工作区。左侧是项目树，中间是当前项目内容，右侧是项目统计、回收站和操作日志。

### 4.1 新建项目

1. 点击“新建项目”。
2. 输入项目名称并确认。
3. 在左侧树中点击项目进入工作区。
4. 通过面包屑返回上级或回到项目首页。

项目树中的数字表示该节点直接或汇总关联的图片/视频数量，右侧“项目统计”展示当前项目的汇总统计，二者统计口径不同，不应简单相加。

### 4.2 导入数据

1. 进入目标项目。
2. 点击“导入数据”。
3. 选择宿主机目录或输入服务器可访问路径。
4. 选择导入模式：
   - **合并导入**：将来源内容并入当前项目。
   - **保持原来的目录结构**：按来源相对目录组织项目内容；适合多级目录数据。
5. 确认后点击“开始导入”。
6. 在导入进度、导入记录和右侧操作日志中查看状态。

支持的文件：

```text
图片：jpg、jpeg、png、bmp、webp
视频：mp4、avi、mov、mkv、wmv
标注：LabelMe JSON、COCO JSON、YOLO txt + data.yaml/dataset.yaml/.names
```

推荐目录示例：

```text
dataset/
├── data.yaml
├── images/
│   ├── train/
│   ├── val/
│   └── test/
└── labels/
    ├── train/
    ├── val/
    └── test/
```

LabelMe JSON 可以包含 `imagePath`、`imageHeight`、`imageWidth`、`view`、`scene`、`keyword` 和 `shapes`。平台会保留视角、场景、模态和其他标签字段，并将矩形标注作为检测框使用。

COCO 通过 `images`、`categories`、`annotations` 和 `file_name` 关联图片及类别。YOLO 类别名称优先从 `data.yaml`/`dataset.yaml` 的 `names` 读取；没有类别文件时只能保存类别 ID，无法可靠显示中文类别名。

YOLO 的归一化框会转换为平台统一坐标。YOLO/COCO 多边形可以导入，但当前统一内部检测标注以矩形框为主，导出时不能保证恢复原始多边形轮廓。

### 4.3 数据筛选、预览和编辑

可以按场景、视角、模态、标签、导入批次、训练/验证/测试划分等条件筛选。大图模式支持：

- 左右箭头或 `A/D` 切换图片；
- 鼠标滚轮缩放；
- `V` 在适应窗口和缩放视图间切换；
- 图片与标注统一缩放、平移；
- 右侧查看尺寸、模态、视角、拍摄时间和 JSON 中的其他标签；
- 页码输入后回车跳转；
- 邻近图片和标注缓存，减少连续翻图等待。

点击“编辑”进入标注编辑。手动标注、分割标注、跟踪标注是互斥模式：

- 手动模式：画出的矩形框就是实际保存的标注。
- 分割模式：画框作为提示，生成的分割结果先作为待确认结果；确认后才写入正式标注。
- 跟踪模式：从当前图片向后处理序列，暂停或切图后可从当前状态继续。

编辑中的移动、缩放、删除、改名和批量改名会写入当前图片的统一草稿并自动持久化。`Ctrl+Z` 只撤销当前图片的编辑记录，切换图片后清空撤销栈。发生异常刷新时，重新进入图片可检查最后一次持久化结果。

### 4.4 删除、回收与恢复

- 项目或图片先进入回收站，不会立即永久删除。
- 单项可恢复或永久删除。
- 回收站支持清空全部内容；该操作不可逆，应确认后执行。
- 删除项目时，回收站以项目为单位展示，避免把子文件夹误当作独立项目。

### 4.5 导出

在项目工作区选择导出格式并提交任务。支持 LabelMe、COCO、YOLO；导出结果进入配置的 `EXPORT_ROOT` 导出目录（默认 `exports/`）。导出期间不要删除源项目或停止数据库/MinIO 服务。

## 5. 资产工作区

顶部“资产”进入资产管理。资产分为：

1. 算法适配器：算法源码、推理/训练能力和格式转换能力。
2. 模型簇：同一模型体系的多个模型版本。
3. 模型版本：预训练权重或训练任务产生的权重。
4. Python 环境：可执行训练/推理的 Conda 打包环境。

模型簇和模型版本是树状结构。模型版本下可以查看实际权重文件，支持下载/导出；导出格式按适配器能力提供 `pt`、`pth`、`onnx` 或原始文件。Python 环境支持 `tar`、`tar.gz` 等 Conda-Pack 形式。

资产导入的一般流程：

1. 点击“登记模型簇”或“登记模型版本”。
2. 填写名称、任务类型、算法适配器、训练数据集、阶段和说明。
3. 选择本地权重或服务器可访问的环境压缩包。
4. 提交后等待 MinIO 归档与元数据登记。
5. 在左侧树展开到最末级文件，右侧下载或导出。

平台在模型、算法和 Python 环境之间保存关联关系。训练/推理选择时优先显示兼容资源；没有自动关联时仍可手动选择，但运行前应确认框架、任务类型、CUDA 和版本兼容。

## 6. 训练工作区

训练页面由左侧训练资源、中间训练配置与队列、右侧训练监控组成。

### 6.1 创建训练任务

1. 选择算法适配器。
2. 选择模型簇和初始化权重。
3. 选择 Python 环境。
4. 分别选择训练集、验证集；支持多个项目/文件夹多选。
5. 使用场景、视角、模态和标签筛选数据。
6. 配置算法适配器提供的训练参数。不同算法参数不应混用；例如 Ultralytics 与 DINO/Faster R-CNN 的参数集合不同。
7. 设置输出与版本。间隔 epoch 默认不保存；需要中间权重时再填写保存间隔。
8. 提交任务，任务进入训练队列。

初始化权重可来自随机初始化、零初始化、预训练模型或已有训练任务产物。若使用已有训练产物并需要恢复优化器/epoch 等状态，使用 `resume`；否则作为普通初始化权重从头训练。

### 6.2 训练队列

任务操作包括：拖拽调整优先级、暂停/继续、重新开始、删除和打开 TensorBoard（若任务产生 TensorBoard 日志）。训练状态、epoch、损失、mAP、ETA 和运行日志由后端任务记录驱动。

删除任务会删除任务记录或取消后续执行；正在运行的任务是否能立即终止取决于当前 worker 是否已响应取消信号。重新开始会重新入队，不等同于从断点恢复。

## 7. 推理工作区

推理页面与训练页面采用同样的资源选择逻辑，但只需要选择一行推理数据源。

### 7.1 创建推理任务

1. 在“数据来源”中选择一个或多个数据集/文件夹。
2. 选择场景、视角、模态、标签等筛选条件。
3. 确认筛选后的图片数量；可以指定随机抽取数量，缺省为全部。
4. 输入任务名称；留空时系统按数据集名称和创建时间自动生成。
5. 选择算法适配器、模型版本和 Python 环境。
6. 检查设备参数：GPU 设备应使用适配器接受的格式，例如 `cuda:0`，不要把仅有数字的 `0` 直接传给要求设备字符串的运行器。
7. 点击“开始推理”。

任务创建后会立即显示到队列；图像数量应等于筛选后的输入图片数量。队列提供拖拽优先级、暂停/继续、重新开始、删除和查看详情。

### 7.2 推理结果

推理 worker 会保存预测框、类别、置信度、原图关联和运行日志。右侧结果预览只在图片上显示框和置信度，不遮挡图片名称；缩略图下方显示当前图片实际出现的类别。

无标注数据仍可以完成推理并保存结果，但不能计算真实 Precision、Recall、mAP。只有带有效真值标注的图片参与评估；局部有标注时，只对有真值的部分计算指标，其余推理结果仍保存。

## 8. 评估工作区

评估不重新选择模型和数据，而是从已有推理记录进入。选择一个或多个推理记录后，可统一展示结果。

主要内容：

- Precision、Recall、mAP50、mAP50-95、F1 等 KPI；
- PR 曲线、F1-confidence、Precision-confidence 曲线；
- 类别 AP 排名；
- 混淆矩阵；
- 错误样本浏览；
- 运行信息、评估洞察、基线对比和报告导出。

### 8.1 错误类型定义

评估使用 IoU 阈值和类别匹配规则：

- **漏检 FN**：真值目标没有被有效预测匹配；显示真值框。
- **虚警/误检 FP**：预测框没有对应真值目标；显示预测框。
- **定位偏差**：预测类别正确，但框与真值的重叠不足以达到正式匹配阈值。
- **类别错误**：预测框与真值框满足预设“同一目标”判断，且达到类别比较所需的 IoU 条件，但类别不同；同时计入一次 FP 和一次 FN。

统一显示约定：真值使用较细实线，预测使用虚线；预测框绘制在前面。错误样本下方必须显示图例，解释颜色、实线、虚线和错误类型。若类别错误，预测类别应显示在预测框旁，真值类别显示在真值说明中。

## 9. 管理员中心与标注规范

管理员中心维护公共的类别层级、目标定义、标注原则和术语映射。

建议配置内容：

- 目标类型树：车辆、军用车辆、装甲车、坦克、IFV、APC 等；
- 中文名、英文名、编码和多个别名；
- 视角、场景/地点、模态等标准代码及别名；
- 类别定义、外形特征、典型车型和标注要求；
- 遮挡、模糊、框边界和中心点等通用标注原则；
- 正确示例和错误示例。

导入时保留原始字段，同时通过别名表映射到标准化代码。这样可以兼容 `IR`、`infrared`、`红外` 等输入，并统一显示为“红外”；`RGB` 显示为“彩色”，`Gray` 显示为“灰度”。

## 10. 设置

右上角设置可以查看或配置：

- 数据浏览根目录；
- 导出目录；
- 数据存储/缓存路径；
- Python 资产和运行环境相关路径；
- MinIO/PostgreSQL 连接相关配置（部署配置通常由 `.env` 或启动脚本提供）。

路径配置原则：浏览目录可以是只读的宿主机目录；MinIO 和 PostgreSQL 数据目录必须由服务独占管理；不要把数据库目录或 MinIO 内部目录当作普通导入目录。

## 11. 典型完整流程

### 11.1 从数据到评估

1. 启动 Podman、PostgreSQL、MinIO 和前端。
2. 登录管理员或普通用户账号。
3. 在数据集中新建项目。
4. 导入 YOLO、COCO 或 LabelMe 数据，确认图片数量和标签数量。
5. 打开几张大图，确认模态、视角、场景和框位置。
6. 在资产中确认算法适配器、Python 环境和模型版本已登记。
7. 在训练页面分别选择训练集和验证集，提交训练任务。
8. 等待训练完成，确认 best/last 权重和日志。
9. 在推理页面选择数据集、筛选条件、模型版本和环境，点击“开始推理”。
10. 在推理队列查看图像数、进度和日志；打开结果预览检查框与置信度。
11. 点击评估页面左侧的推理记录。
12. 查看 KPI、曲线、混淆矩阵和错误样本；双击错误样本查看大图。
13. 导出评估报告，必要时将模型登记为新的版本并重新迭代。

### 11.2 只有推理没有真值

可以直接导入无标签图片并运行推理。此时：

- 推理框和结果文件正常保存；
- Precision、Recall、mAP 等真实指标不可计算；
- 评估页应明确显示“无真值/等待标注”，不能把伪造或默认值当作真实指标。

## 12. 常见问题

### 页面打不开

检查 `restart-det-dashboard-podman.bat` 是否成功结束，并确认 5173、4177 端口没有被其他进程占用。查看 `DD-runtime\logs\api.log` 和 `web.log`。

### PostgreSQL tunnel did not become ready

确认 Podman machine 正常运行，执行 `podman info`；然后检查 PostgreSQL 容器健康状态、SSH 配置和 Windows 端口占用。不要在同一个端口上重复启动旧隧道。

### MinIO 中看到很多 `xl.meta`

这是正常的 MinIO 内部对象格式，不表示 `.pt` 或 JSON 丢失。通过平台的资产树、下载或导出接口访问模型和环境，不要直接改 MinIO 数据目录。

### `Unexpected end of JSON input`

通常表示后端在连接中断、隧道断开或服务异常时返回了空响应。先看 API 日志和 Podman 隧道日志，再确认数据库/MinIO 健康状态；不要立刻重复导入同一批次，以免产生重复任务。

### `socket hang up`

通常是大文件上传经过 Podman SSH 隧道时连接被重置。当前导入链包含上传重试和串行化保护；应先确认最新批次状态。历史失败批次可以保留作为审计记录，只有确认没有有效数据时再清理。

### 推理图像数为 0 或进度不动

检查筛选条件是否筛空、数据集是否有图片记录、模型/环境是否关联成功，以及 API 日志中的输入扫描和 worker 日志。无标注不会导致图像数为 0；它只影响真实评估指标。

### 评估指标为空

确认推理记录已完成，输入图片存在有效真值标注，类别映射没有缺失，并检查评估日志。没有真值时应使用结果预览，而不是期待 Precision/Recall/mAP。

### 缩略图或大图加载失败

检查 MinIO 服务、对象是否存在、缓存目录是否可写，以及 API 日志中的对象 key。删除或移动原始文件后，独立对象模式仍应可用；链接/fallback 模式依赖原路径。

## 14. 当前版本边界

- PostgreSQL 和 MinIO 是核心持久化服务，Node API 负责业务编排和任务执行。
- 任务 worker 目前依赖当前运行节点可访问的 Python、CUDA、算法源码和环境；跨节点调度不是默认能力。
- 内部标注模型以矩形检测框为主，多边形导入会保留部分原始信息但不保证按原多边形复原。
- 视频已经支持导入和抽帧关联；完整时间轴级视频标注能力仍应按专用视频工作台继续扩展。
- 权限、共享和协同标注入口已经具备，但生产部署仍应补充 HTTPS、强密码、备份策略和更严格的网络隔离。
